# Workflow rules are checked in CI on the pull request and enforced by a ruleset on main

`pr-check` checks that the pull request title is a Conventional Commit summary, that the body has a `Closes #<n>` line for each open issue it closes, and that the branch is `issue-<n>-<slug>` for one of those issues; `ci` runs ruff and pytest. Squash merges and merge commits both take the pull request title (`squash_merge_commit_title` and `merge_commit_title` set to `PR_TITLE` by `scripts/bootstrap.sh`), so the title check is what keeps the history on `main` in Conventional Commits.

The `main` ruleset, also set by `scripts/bootstrap.sh`, makes both checks required, requires a pull request (with no approvals, since a sole maintainer cannot approve their own), and blocks force pushes and deletion. Repository admins may bypass it only when merging a pull request, so a broken check cannot block all work while direct pushes to `main` stay impossible. Required checks are matched by job name, and a required check that never runs blocks merging, so the workflows have no path filters.

Local hooks (pre-commit for commit messages and branch names) were rejected: they need an install step in every clone, are skipped silently when not installed, and check commit messages that squash merging discards. The individual commits of a pull request are not checked either: whether they stand alone, which is what allows a merge commit instead of a squash, is judged when merging. Bypass for admins at all times was rejected because it allows direct pushes to `main`; no bypass was rejected because a broken check would then need the ruleset disabled to merge anything.
